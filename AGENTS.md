# AGENTS.md

This file provides guidance to AI agents when working with code in this repository.

> **Commit your work, one logical unit per commit.** You may commit without being asked, and should: keep unrelated changes on separate branches, one feature (or fix) per branch; a big feature may be split into several commits. Every commit must be valid on its own: the pre-commit hooks and the tests pass on it (see *Commands*).
>
> **Never commit to `main`: changes reach it only through pull requests.** If the checkout is on `main` or on a branch of unrelated work, branch off the latest `main` before your first change and commit there. The user pushes the branch and opens the pull request, unless they ask you to (the dev container cannot push).

## Commands

`git commit` runs the hooks from `.pre-commit-config.yaml` (CI runs the same ones) on what it commits, so don't run `prek` by hand; while working, run the tests of what you change (`cargo test -p ..`). The slow hooks of the manual stage (`wasm-test`, `web-e2e`, `gui-e2e`) run only in CI: run one locally only where a change is more likely than not to break it.

```sh
prek run --all-files --stage manual gui-e2e   # one slow hook, if needed
```

The hooks are `cargo-fmt` (needs **nightly** rustfmt: `rustfmt.toml` uses unstable options), `cargo-clippy` (`-D warnings`), `cargo-clippy-wasm` (the crates that run in the browser, for `wasm32-unknown-unknown`, configured by `clippy-wasm/clippy.toml`), `cargo-test`, `cargo-doc` and `cargo-sort`.

- A single test: `cargo test -p tournament-engine <test_name_substring>`; integration tests live in `tournament-engine/tests/` (`--test full_tournament`). Doc tests count.
- **WebAssembly.** `plugin-factory`, `tournament-engine`, `tournament-app` and the library of `tournament-cli` (`--no-default-features`, i.e. without `terminal`) must build for and pass their tests on wasm. `tournament-web` and `tournament-browser` only run in a browser: their tests are `#[wasm_bindgen_test]`s in wasm-only modules, run in headless Chrome. The manual-stage `wasm-test` hook runs all of them in CI (needs `wasm-pack`, Chrome and chromedriver). A single crate or file: `wasm-pack test --node tournament-engine --profile wasm-test [--test <file>]` (`--headless --chrome` for the browser crates; the profile drops debug info, which more than halves the time). Doc tests and the benchmark run natively only. System randomness (`thread_rng`, `Uuid::new_v4`) is enabled on wasm by the final application (`getrandom/wasm_js`, `uuid/js`); libraries must not enable it in their normal dependencies.
- **End-to-end tests** (`#[ignore]`d, so `cargo test --workspace` needs no browser): `e2e-harness` serves a built page and drives headless Chrome over WebDriver (`thirtyfour`, starting chromedriver itself, downloading it if needed, or the one `E2E_CHROMEDRIVER` names) through a `Page`. Each page wraps `Page` in what an operator does there: `tournament-web-e2e`'s `Terminal` (page built by `cd tournament-web && trunk build`; hook `web-e2e`) and `tournament-gui-e2e`'s `Gui` (page built in seconds by `CARGO_TARGET_DIR="$PWD/target/e2e" dx build -p tournament-gui --profile wasm-e2e --debug-symbols false`: the profile skips wasm-opt and LTO, and has no debug assertions, under which dioxus-web would try to reach `dx serve`; hook `gui-e2e`, needs `dx` of the `dioxus` version in `Cargo.lock`). Read their docs for what they offer, and extend them rather than repeating WebDriver calls in tests. A single one: `cargo test -p tournament-gui-e2e <name> -- --ignored` after the build.
  - Chrome prefers English and opens at 1280×900, where the GUI shows every column. Headless Chrome refuses persistent storage, so the storage warning shows in every GUI test.
  - Translated texts wrap every variable in U+2068/U+2069 (`e2e_harness::ISOLATION_MARKS`): `Page::expect_texts` and the `Gui`'s buttons ignore them, `Page::expect_text` does not, so use it only for texts without variables.
  - Sides of a match come from the random seed: a GUI test must not depend on which side an entrant is on.
  - A test fails if the page logs an error (e.g. a wasm panic) or axe-core finds a WCAG 2.1 A/AA violation at its end; call `check_accessibility` for states in between. A failure leaves `screenshot.png` and `report.txt` in `target/e2e-failures/<test file>/<test>/` (CI artifact `e2e-failures`).
  - Terminal tests cover only what the page does (input, history, URL, reloads, leaving); what a line shows belongs in `tournament-web`'s `wasm_bindgen_test`s.
  - Watching: `E2E_HEADED=1` opens a window, `E2E_PAUSE=<seconds>` pauses after each `Terminal` action (give a new action a pause too), `E2E_LINGER=<seconds>` keeps the window open after the test (add `--test-threads=1`).
- Benchmark: `cargo bench -p tournament-engine --bench large_tournament` (criterion). Example: `cargo run -p tournament-engine --example run_tournament`.
- CLI: `cargo run -p tournament-cli -- [FILE]` (`tournament-cli/README.md`). Web: `cd tournament-web && trunk serve` (`tournament-web/README.md`). GUI: `dx serve -p tournament-gui` (`--hot-patch` patches Rust code into the running page); release build `dx build -p tournament-gui --release --debug-symbols false` (the debug build tries to reach `dx serve`), `--base-path <path>` for a page served under a path, `TOURNAMO_MEDIA_OWNER="<name>, <town>"` for the media owner the help names (CI: repository variable `MEDIA_OWNER`) (`tournament-gui/README.md`).
- **Dev container** (`.devcontainer/`, see its `README.md`): reaches only the hosts in `proxy/allowed-domains.txt` (through a proxy; anything else fails), cannot push, and `.devcontainer`, `.git/hooks` and `.git/config` are read-only there. If a build needs another host, say so rather than working around it.
- Profiles: `release-checked` (release with debug assertions and overflow checks), `wasm-test`, `wasm-release` (what `dx build --release` uses for the GUI; keep it under 1 MB gzipped), `wasm-e2e` (the GUI for its e2e tests).
- Keep `Cargo.toml` dependency lists sorted (`cargo-sort`). Versions are declared only in the root `[workspace.dependencies]`; members use `dep.workspace = true`. Exception on purpose: `plugin-factory` and `plugin-factory-derive` declare everything themselves (including `version`/`edition`/`license`) so they can leave the workspace together; don't give them workspace references or let them depend on the other crates.
- `undoable-state-machine` is a git dependency (same author) pinned to a tag of its repository: its log entries are part of every saved competition. Pick up a change by tagging a new version there and changing the `tag` in the root `Cargo.toml`, after checking that saved logs still load.

## Architecture

Crates: `plugin-factory` (+ `plugin-factory-derive`: generic plugin axes, catalog, schemas, drafts, compatibility; depends on nothing else here), `tournament-engine` (the library), `tournament-app` (what the GUI does, without UI), `tournament-gui` (Dioxus in the browser; e2e tests in `tournament-gui-e2e`), `tournament-browser` (browser APIs for the GUI), `tournament-cli` (REPL on the engine), `tournament-web` (the CLI's command line in the browser; e2e tests in `tournament-web-e2e`), `e2e-harness`. `DESIGN.md` is the authoritative design record, with rationale and rejected alternatives: read the relevant section before changing a mechanism. Sections marked *planned* are not implemented; some type names in it may lag behind renames.

### Global constraints (apply everywhere)

- **State changes only through logged transitions.** Progress is `CompetitionStateMachine` (an `undoable-state-machine` `StateMachine<Competition, CompetitionTransition>`, an enum of the engine's transitions); undo replays the remaining log from the initial state. `Competition`'s mutators are crate-internal on purpose. `undo`/`redo` are per session: an `undoable_state_machine::SessionHistory` (not persisted) records the entries the session appended as actions and undoes/redoes them with explicit undo entries. Operations appending an action take the history (`SessionHistory::apply_new`, `CompetitionStateMachineExt::undo_match_result`, `reconfigure_phase`); `StateMachine::apply_new` appends outside any history (the seed, tests). `Transition::apply` cannot fail: whatever makes a transition inapplicable belongs in `check_applicable`.
- **Determinism under replay.** `Transition::apply` is a pure function of state plus the transition's data. Randomness comes from the competition seed (`SetCompetitionSeed`); a format draws from `PhaseData::rng`. Ids (`MatchId`, `RankingId`) are UUIDv5s derived from content. Anything non-derivable (names, timestamps, external ids) arrives as transition data.
- **Runtime-pluggable, third-party-open axes on `plugin-factory`.** Each axis (`PhaseFormat`, `SliceRanker`, `MetricsCalculator`) is a public unsealed trait used as `Box<dyn Trait>`, declared with `#[plugin_factory::axis]`, with `plugin_factory::Plugin + DynClone` as supertraits and `dyn_clone::clone_trait_object!(Trait);`. A plugin derives `Plugin` (`#[plugin(id, label, description, declare_static, declare)]`; its schema comes from its fields, each with `#[plugin(label = ..)]`) and registers with `#[register]` on its axis impl, which also tags it for `typetag` with its id. Facts a plugin provides/requires go through `plugin_factory::compatibility::Declaration`; the engine's facts are in `plugins::facts`. A plugin's runtime state (e.g. the bracket) is a `#[serde(default)] #[plugin(skip)]` field. A phase is always ranked by a `HierarchicalRanker` of its slice rankers (the ranker is not an axis). A criterion like `MorePoints` implements `RankingCriterion` (metric type + comparison), declares `declare_static = requires_metric::<Self>` and registers with `register_criterion!(MorePoints)`. Likewise a calculator like `PointsCalculator` implements `Calculator` (metric type + updates after a match and a bye), declares `provides_metric::<Self>` and registers with `register_calculator!(PointsCalculator)`. No closed enums, generics on entities, or `enum_dispatch` (DESIGN.md explains why generics fail with `typetag`). A new plugin needs only its derive and registration; no consumer may grow a table of plugins.
- **A phase's plugins are the composite `PhasePlugins`** (`Configurable`: format, ranking, metrics). In production they are built only from the draft `Competition::phase_draft` creates (or deserialized), answered with configs (`Draft::with(field, PluginConfig::of::<P>().with(..))`, `Draft::with_defaults`). `Draft::add_implied` appends, for each fact nothing provides, the single fieldless plugin providing it (idempotent); `Draft::build` adds nothing, so calling `add_implied` first is the caller's choice. Calculators are a `DependencyOrderedSet` (running order; rejects duplicates and cycles), slice rankers an ordered `Vec`. `AddPhase::check_applicable` runs `compatibility::check`. Reconfiguring: `Phase::config` → `Draft::with_answers` → `CompetitionStateMachineExt::reconfigure_phase`, which appends a `LogEntryKind::Replace` of the phase's `AddPhase`.
- **No untyped data bags.** Open-ended data is keyed by Rust type through `TypeMap` (`type_map.rs`). Metrics are `TypeMapValue`s. Consumer data is an annotation on the entity, written by the transition creating it (`Entrant::new(id).with_annotation(..)`).
- **No personal data in the log** (it replays as written and cannot be partly deleted): names live in `People` (`tournament-app/src/people.rs`, re-exported by the CLI), keyed by `EntrantId`, saved next to the log.
- **Scores** are `Score` (`score.rs`): a finite `f64` (`-0.0` made `0.0`) with `Eq`, `Ord`, `Hash`, made by the `const fn` `Score::new(0.5)`; a non-finite result panics.
- **Numeric ranges in the schema.** A numeric `FieldKind` carries `IntegerRange`/`DecimalRange` (`min`, `max`, `multiple_of` anchored at 0): the type declares it in `FieldType::kind`, a field narrows it with `#[plugin(min = .., max = .., multiple_of = ..)]`; the draft rejects out-of-range numbers (`ConfigError::OutOfRange`) and prompters ask within it.

### Persistence

- Two paths: a `Competition` snapshot, and the transition log (deserializing replays it; a log that doesn't replay fails to load). The CLI saves `{"format", "log", "people"}` as JSON; the app stores each log entry and each person as a JSON record. Neither saves the undo history.
- Trait objects serialize via `typetag` with **adjacent tagging** (`#[typetag::serde(tag = "type", content = "value")]`); internal tagging breaks non-self-describing formats like postcard. Tests exercise postcard and serde_json.
- **Saved data is a promise to users** (since v0.1.0): a change to what is saved must keep older saves loading; note it under *Unreleased* in `CHANGELOG.md`, as any change an operator notices. **Golden saves** (`tournament-app/tests/golden_saves.rs`, DESIGN.md *Golden saves*): competitions as released versions saved them, which must load and replay into the competition saved with them; never edit or regenerate them. Before every release, script any new format or saved feature in the generator, write the release's saves (`cargo test -p tournament-app --test golden_saves -- --ignored write`) and list them in `SAVES`.
- **A change of what is saved** raises `file::Format::CURRENT` and adds the converter from the format before to `tournament-app/src/file/convert.rs` (the build fails without it; rules in its module doc), unit-tested there, and is noted in `CHANGELOG.md`; the release writes its golden saves as usual. `File::read` converts an older file before reading it, so the engine's types read only the current layout: a consumer that serializes a bare `Competition` or log outside a file gets no versioning.
- **Tags are persistence contracts.** A transition is saved under its variant's name in the enum `CompetitionTransition` (renaming one needs a converter); a plugin's tag is its `PluginType::ID` (e.g. `tournament_engine::points`); both pinned in `tests/transition_log_serialization.rs`. New plugins/metrics/annotations need an explicit tag; never change an existing one.
- `IdMap` (`map.rs`) and `TypeMap` wrap `IndexMap` and serialize as sequences in insertion order, which code may rely on (matches are kept in scheduling order). A match's number is a field (`Match::number`), set by the format (`NewMatch::with_number`, as a bracket does from `BracketPairing::number`) or else by scheduling order; `MatchId` does not include it.

### Engine data flow

`Competition` → `Phase` (its `PhasePlugins`: format, match format, slice rankers, metrics calculators; and its `PhaseData`: `matches`, `byes`, `rankings`) → `Match` / `Bye` / `Ranking`. On `StartCompetition` and after every result the format schedules a `Schedule` of matches and byes (`create_new_matches(&PhaseView)`: the `PhaseData`, and the standings on request). A bye counts once its ranking reaches it (`Bye::is_reached`: no open match of the ranking in an earlier round); then each calculator's `update_after_bye` runs. On `ReportMatchResult` the match is appended to its rankings' `played_matches` and each `MetricsCalculator` updates incrementally (`update_after_match_result`, i.e. `Calculator::after_match`, seeing the *old* metrics of the calculators before it). This is the hot path, run once per result by every replay (undo, redo, load). Ranks are not stored: `Phase::standings` sorts by the ranker on every call (`Standings`, borrowing the phase: best first, each row its `Ranking`, rank and unique rank), so a reader asks once; serializing a phase writes them, for the saved layout. `rank_by` looks up each ranking's metric once per sort, not per comparison. The engine knows nothing of display except a calculator's optional `MetricColumn` (header plus a `Cell` made by `ToCell`: a `Score`, signed or not, a round, which the app names by its stage where the format names one, or a `Phrase`) and `PhaseFormat::stage` (a `Stage`: a `plugins::Phrase` of key, numbers and English `Display`).

### App

`tournament-app` is what the GUI does without UI, tested natively and in wasm; it must not depend on a UI crate or the CLI. Read the module docs for details.

- `session.rs`: `Session` runs one competition for an operator. Each action (`add_entrant`, `add_phase`, `edit_phase`, `start`, `report`, `report_entered` (a typed result: `"3 1"`, `3x`, or part of the winner's name, never guessing among several matches; `read_entered` previews it), `undo_report`, `undo`/`redo`, ...) becomes transitions through its `SessionHistory`, or is refused with a typed error (`error.rs`; engine errors recognized by downcasting the `TransitionError`, anything unknown is `Rejected`). A refused `undo_report` or `edit_phase` names every match whose result is in the way (`DependedOnBy`, `ResultDoesNotFit`), found only once it was refused, by a dry run of the change (`CompetitionStateMachineExt::conflicts_of`, which covers undoing or replacing an `Apply` in effect, not a redo or the undo of a replacement). It hands out plain data for screens (`view.rs`: entrants, `rounds`/`round`, `playable`, `rounds_view` (what the list of rounds shows: the list chosen, a typed entry, where the focus goes on), `standings`, `winners`, `actions`, ...; `session/bracket.rs` for the bracket a format hands out (`PhaseFormat::bracket`), drawn in sections by the stage annotations of the engine's knockouts; `session/cross_table.rs`). `session.rs` holds the struct and what every part needs; each job is an `impl Session` of its own in `session/`: `storage.rs` (load, save, catch up, import, export), `entrants.rs`, `phase.rs`, `scale.rs`, `report.rs`, `entry.rs` (typed results), `undo.rs`, `views.rs`.
- `result_form.rs`: `ResultForm` enters the result of a match from the template of its match format (`Session::result_form`, `Session::report_form`): values and parts by path, the result chosen or else suggested (`MatchFormat::suggest`), warnings (a value above the usual, a result against the suggested one), never a refusal for a sport's rules; text typed that its field cannot take (`enter`, e.g. a count above 65535) stays shown with why and keeps the match from being reported (`rejected.rs`'s `Rejections`, which `PhaseForm` keeps for its numbers too). `read_score` reads a score typed or pasted as one word (`21-17`, `21–17` as shown, `9.5-10`), for every consumer (typed results, the CLI's `report`). The form of a match the session reopened starts out at the result it had; `enter_scores` replaces everything entered.
- `form.rs`: `PhaseForm` configures a phase (the GUI counterpart of the CLI's questionnaire): `view()` is a `FormView` generated from the draft's schema, with issues and warnings as `Text`s. New forms follow suggestions until ranking or scoring is edited; then both sections are kept until `apply_suggestions` replaces them and resumes following. Existing and undone phases start customized. All registered choices stay visible; incompatibilities are reported after selection, and an invalid phase cannot be added or saved. `draft()` goes to `add_phase`/`edit_phase`.
- `i18n.rs` (Fluent): every error is a `Message` saying a `Text`, and an engine refusal the app knows is a `Refusal` (`error.rs`, the one list of downcasts) (key plus variables; what a library says about why is its detail, `with_detail`, not a variable). Messages are lowercase fragments like the `Display`s; `Translator::sentence` makes a sentence. A `Translator` of a `Language` holds the app's messages (`locales/<lang>/app.ftl`; an error's `Display` is its English message there, so its variants carry no `#[error(..)]` text) plus a consumer's `Resources`; missing messages fall back to English, numbers are written as the language writes them. Plugins are translated in `locales/<lang>/plugins.ftl` as attributes of `plugin-<id with :: as ->` (`PluginText`: `.label`, `.description`, `.column`, `.field-<name>`, `.field-<name>-description`, a format's `.stage-<key>`, a calculator's `.cell-<key>`, a match format's `.level-<key>`, `.value-<key>`, `.reason-<key>`); the phase's own fields are attributes of `phase`. **A new engine plugin needs its German there** (a test checks every plugin and nothing else; a format naming stages is listed in its `stages`, a metric showing phrases in `phrases_in_cells`; the phrases of a match format are found from a `ResultForm`). `i18n::check` tests a consumer's resources.
- `storage.rs`: the async `Storage` trait (`fn .. -> impl Future`, not dyn-compatible, futures need not be `Send`): `list`, `read(key)`, `write` of a `Save` (the listing and one record: the competition's file without the name, rewritten whole; the write starts when called and its future borrows nothing, so saves are stored in the order they are made; a record without the competition the log replays into, by an older version, is an unsaved change), `rename`, `delete`. A save is `to_save()`, the write, `mark_saved(&save)` (`Session::save`), so no borrow of the session is held across the write; the session counts its changes (`changes()`), so a failed write leaves them for the next save. Catching up with another tab's saves: the read, `catch_up_with` (`Session::catch_up`), which reads the stored log without replaying it and applies the entries after the session's. `MemoryStorage` finishes every future at once; tests poll once with a no-op waker (`now` in `session/tests.rs`).
- `file.rs`: a competition moves as JSON `{"format", "name", "log", "people"}` (the CLI's file plus the name, so each opens the other's; `file::Format` is raised with every change of what is saved, older versions refuse a newer one): `Session::export`, `Session::import`, `Stored::export` (also for a log that no longer replays). `File::read` reads every file (the CLI's too), converting an older format first (`file/convert.rs`).

### GUI

`tournament-gui` is a Dioxus 0.7 app built by `dx` (`Dioxus.toml`, `index.html`, plain CSS in `assets/style/`, a file per screen or part, loaded through `asset!()` in the order `main.rs`'s `STYLES` lists, which is that of the cascade). Components only lay out what `Session` hands out; **logic belongs in `tournament-app`**, where it is tested. Its tests are the e2e tests of `tournament-gui-e2e`; it is linted for wasm by `cargo-clippy-wasm`.

- Modules: `main.rs` (the page: one `Header` for every screen, `Page` with the state every screen shares, the list of competitions, the one named after `#`, or the help at `#help`; the footer links to the help and the repository), `competitions.rs`, `help.rs`, `competition.rs` (`Ctx`: session, lock, signals), `setup.rs` (entrants, phase, start), `phase/` (the `PhaseForm`: in place for a new phase, a summary and an edit dialog once added; `fields.rs`, `lists.rs` for lists of plugins, `summary.rs`), `play.rs` (after the start: matches, standings), `result/` (a result entered beyond who won, from a `ResultForm`: `quick.rs` in the row of the match, `dialog.rs`, `value.rs` for one side's value, `reported.rs` for a finished match), `bracket.rs`, `cross_table.rs`, `toggletip.rs`, `announcement.rs` (the live region; `Ctx::announce` after a successful `act`), `notices.rs` (errors with folded detail, the storage warning), `focus.rs` (moving the focus on after a change), `install.rs`, `theme.rs`, `icons.rs`, `i18n.rs`, and `src/components/` (`select`, `dialog`: copied by `dx components add` on `dioxus-primitives`; their styles are changed in their own `style.css`, each change marked).
- Every text goes through the `Translator` in `Ctx`: `tr.get("key")`, `t!(tr, "key", name = value)`, `tr.plugin(id, PluginText::Label, english)`; messages in `locales/<lang>/gui.ftl`. Errors show in a `role="alert"` as a sentence; a plugin's label standing alone is `capitalized`.
- `Ctx::act` runs an action, then saves in a task that outlives the screen and holds the lock until written. One tab at a time changes a competition: the one holding its Web Lock (`tournamo.competition.<key>`); others are read-only (`Ctx::actions()` all false), catch up when the writer posts on the `BroadcastChannel` `tournamo.saved`, and take over when the lock is released.
- Layout and look (DESIGN.md, *Layout*, *The bracket*, *The cross table*): a sticky bar on top (`--bar-height`), cards in columns where there is room, names never cut, 44px buttons where the pointer is coarse. Colours only through the tokens of `style/tokens.css`, each `light-dark(light, dark)`; a new colour is a new token meeting WCAG AA in both.
- Accessibility is WCAG 2.1 AA: semantic HTML, buttons named by what they do ("Alice wins", `aria-label` where the text is ambiguous). Buttons that become unavailable while focused are `aria-disabled`, not `disabled` (which drops the focus). After a change that moves or removes what had the focus, move it on (`focus::focus_later`, `focus::use_focus`).
- PWA: `public/` (copied next to `index.html`, so URLs are relative) holds the manifest, icons, the service worker `sw.js` and `pwa.js`.

### Browser

`tournament-browser`, each part testable in headless Chrome: `indexed_db.rs`'s `IndexedDb` (the app's `Storage`; raise `VERSION` with every change of its object stores; a write is one transaction over the listing and the record, spawned on wasm-bindgen-futures' executor when called, since the transaction stays active only in the microtasks after a request and transactions run in the order they are created; competitions of version 2 are read from their old stores until their next write moves them), `lock.rs` (Web Locks, bound by hand), `channel.rs` (`Events`, `Broadcast`), `persistence::persist`, `file::download`.

### Web

`tournament-web/src/lib.rs` holds what is testable: `LocalStorage` (the CLI's `Storage` on local storage) and `Shell`, which runs a line against a CLI `Session` and returns `Reply`s. For questions (`add-phase` without a format, `edit-phase`) the shell keeps the `fill_phase_async` future and resumes it with each line (`questions.rs`'s `LinePrompter`, polled with a no-op waker). `main.rs` only wires up the page. It is a thin text layer on purpose; the GUI is a separate app, not built on it.

### CLI

`tournament-cli/src/lib.rs` holds everything testable: `command.rs` parses a line into a `Command`, `session.rs` executes it and saves/loads through a `Storage` (`storage.rs`: bytes under a name; `FileStorage` writes atomically, tests use `MemoryStorage`). `questionnaire.rs` fills a `Draft` of any `Configurable` from its schema, knowing no concrete plugin: the logic is the async `fill_async` over an `AsyncPrompter`; every `Prompter` (`Terminal`, `AcceptDefaults`) is one by a blanket impl, and the synchronous `fill` polls once. `fill_phase`/`fill_phase_async` additionally offer the configured format's ranking and scoring suggestions through `PhasePlugins::default_value`. Stopping is `questionnaire::Error::Cancelled`. `add-phase <FORMAT> [FIELD=VALUE]...` looks the format up in the catalog; everything else follows `PhaseFormat::suggestions`. The default feature `terminal` gates what needs a terminal (`inquire`, `rustyline`, the binary), so the library builds for wasm without it. The standings show the column of every calculator offering one, in running order.

## Writing tests

- **A test names only what it is about.** Build test data with a builder and leave everything else to its defaults. Prefer builders over helpers with positional parameters; don't add a helper that only wraps a builder with fixed arguments. When a builder lacks something, extend it (with a sensible default).
- **Engine builders** are behind the `test-util` feature: `PhasePluginsBuilder` (defaults: round robin, empty ranking, no metrics), `PhaseBuilder` (a standalone `Phase` for plugin unit tests, plus `add_players`). Plugins with fields have constructors behind the same feature (`PointsCalculator::new(..)`, `SingleElimination::new()`); a new one gets one under `#[cfg(feature = "test-util")]`, and an ungated doc comment must not link to it. The engine's own tests get the feature through a dev-dependency on itself.
- **Every test also runs in WebAssembly.** The wasm runner silently skips plain `#[test]`, so each test module (and integration test file) of a wasm crate imports `#[cfg(target_arch = "wasm32")] use wasm_bindgen_test::wasm_bindgen_test as test;` (a nested module with `use super::*;` needs it too, else `test` is ambiguous); `cargo-clippy-wasm` rejects a plain `#[test]`. A test that can't work in wasm (e.g. `catch_unwind`) gets `#[cfg_attr(target_arch = "wasm32", ignore = "<why>")]`.
- **Where tests live.** A module's unit tests are inline (`#[cfg(test)] mod tests { .. }`) until they outweigh its code; then they move to `<module>/tests.rs` (`#[cfg(test)] mod tests;`), split further by job where they grow large (`tournament-app/src/session/tests/`).
- **Configs only where configuration is tested**: drafts (`Competition::phase_draft`, `Draft::with`, `PluginConfig`) belong in tests of configuration, implied plugins, or a consumer's configuring; other tests build plugins directly.

## Working style

- Agents work in the dev container, where every edit and command is accepted: use whatever tool available there suits the task (Edit/Write, `sed`, scripts, ...). If a task calls for a tool the container lacks, get on with the task: install the tool at runtime if possible, otherwise work around it. Either way, tell the user clearly which tool was missing and why it is needed, so it can be added to the container (that needs a rebuild, so not during the task).
- **Planned features are GitHub issues** of `blacktemplar/tournamo`. Read them with `gh` (`gh issue list`, `gh issue view <number> --comments`) when a task refers to one or touches what one plans. Write to GitHub (issues, comments, PRs) only when explicitly asked.

## Conventions

- The user prefers invariants enforced by types/the compiler over runtime checks or self-reported plugin facts, and is cautious about costs on the result-reporting hot path.
- Plugin labels and descriptions follow "Labelling a plugin" in the docs of `tournament_engine::plugins` (partly checked by a test). The answer a field offers is `#[plugin(default ..)]`; `#[serde(default)]` only governs loading.
- Doc comments follow KISS: what a public item does and everything a caller needs (contract, panics, errors, ordering), nothing more. No history or rejected alternatives (those go in `DESIGN.md`); reasoning a *maintainer* needs goes in a plain `//` comment.
